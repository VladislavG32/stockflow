# StockFlow

Система автоматизации складского учёта: каталог материалов, поставщики, регистрация поступлений, остатки и план пополнения.

Учебный проект по дисциплине «Автоматизация процессов жизненного цикла программных средств». Автор: **Остапенко Владислав Русланович**, группа **241-3211**.

## Возможности

- Материалы с кодом, категорией, единицей измерения и порогами запаса.
- Справочник поставщиков и контактных данных.
- Поступления с уникальным номером, датой, количеством и примечанием.
- Остатки как сумма поступлений; рекомендации при остатке строго ниже минимума.
- Изменение порогов, поиск, фильтры, сортировка материалов и экспорт полного плана в CSV.
- Русский адаптивный интерфейс, проверка форм, сообщения об ошибках и сохранении.

Количество задаётся целыми числами. Списания, резервы, заказы, пользователи и роли не реализованы. Без аутентификации приложение предназначено для доверенной локальной / host-only сети; публикация в открытый Интернет требует отдельной проработки доступа.

## Технологии и архитектура

Next.js 16 / React 19 / TypeScript, PostgreSQL 17, Drizzle ORM, Zod, ESLint, Node.js, Docker Compose, TeamCity Kotlin DSL. Версии закреплены в `package-lock.json`; рекомендуется Node.js 24 LTS (минимум 20.9).

`page.tsx` получает снимок из PostgreSQL и передаёт его клиентской панели. API Route Handlers проверяют JSON и передают операции в `repository.ts`. Zod и ограничения PostgreSQL проверяют данные. Остатки вычисляются SQL SUM, а справочники и журнал читаются в транзакции REPEATABLE READ. После сохранения интерфейс повторно запрашивает единый снимок.

Схема текущей ветки — только миграция `0000`. Цены и документы поступлений из подготовки ЛР №8 сюда не перенесены.

## Запуск в Docker

Нужны Docker Engine с Linux-контейнерами и Docker Compose с поддержкой `--wait`. Наличие одного Docker CLI не означает доступность Engine.

1. Скопируйте `.env.example` в `.env` (`Copy-Item .env.example .env` в PowerShell или `cp .env.example .env` в Bash). Если `.env` уже есть, сохраните его и проверьте параметры.
2. Замените `replace_with_random_hex` одним случайным hex-паролем в `POSTGRES_PASSWORD` и `DATABASE_URL`. Не публикуйте `.env`.
3. Выполните:

```bash
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps -a
```

Откройте [localhost:3000](http://localhost:3000). Compose запускает БД, одноразовый migrator, затем приложение. `Exited (0)` для migrator — штатный результат. Новый каталог пуст; добавьте материал и поставщика, затем поступление.

Остановка с сохранением данных: `docker compose down`. Повторный запуск: `docker compose up -d --wait`. **Не используйте `down -v`**: он удаляет том PostgreSQL. Смена пароля в `.env` не изменяет пароль роли уже существующей БД. Не меняйте имя Compose-проекта и расположение рабочего развёртывания без проверки используемого volume.

## Локальная разработка

Подготовьте `.env` по образцу. Для npm-команд `DATABASE_URL` должен указывать на локальный PostgreSQL (например, `127.0.0.1:5432`), а не на имя сервиса `db`.

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d db
npm ci
npm run db:migrate
npm run dev
```

Можно использовать отдельно установленный PostgreSQL 17 вместо Docker. Миграции выполняйте только на выбранной базе разработки. CLI читает `.env`; избегайте отличающегося `DATABASE_URL` в `.env.local`, чтобы приложение и CLI не подключились к разным БД.

Необязательная команда `npm run db:seed` добавляет явно обозначенные примеры DEMO, допускает повторный запуск и не запускается автоматически. Она предназначена для базы разработки.

## Проверки

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run test:infra
npm run build
```

Unit-тесты проверяют расчёт пополнения, валидацию, CSV и выборку материалов. `test:infra` проверяет конфигурацию и защитные отказы скриптов; он не запускает TeamCity или Docker. Нужен рабочий Bash. В Windows, если `bash` ведёт в неустановленный WSL, передайте Git Bash:

```powershell
$env:STOCKFLOW_BASH = 'D:/program/Git/bin/bash.exe'
npm run test:infra
```

Укажите путь своей установки Git. HTTP-интеграция требует работающего приложения и **той же тестовой БД**:

```bash
npm run test:integration
```

`BASE_URL` по умолчанию — `http://127.0.0.1:3000`. Например, в PowerShell: `$env:BASE_URL='http://127.0.0.1:3001'`. Тест создаёт уникальные QA-записи и очищает их после проверки идентичности подключения. Не направляйте его на рабочие стенды.

Для production-сборки локально выполните `npm run build`, затем `npm start`. Скрипт запуска копирует статику в standalone-каталог; доступны `npm start -- --port 3001 --hostname 127.0.0.1`. Перед повторной сборкой остановите этот сервер, особенно в Windows. Сборка не требует подключения к БД.

## API и данные

| Метод / адрес | Назначение |
| --- | --- |
| GET `/api/health` | Сохранённый контракт: `{"status":"ok","service":"stockflow"}` |
| GET `/api/ready` | Доступность PostgreSQL и трёх таблиц; 200 / 503 |
| GET `/api/dashboard` | Единый снимок данных склада |
| GET/POST `/api/materials` | Список / создание материала |
| PATCH `/api/materials/:id` | Минимальный и целевой запас |
| GET/POST `/api/suppliers` | Список / создание поставщика |
| GET/POST `/api/receipts` | Список / регистрация поступления |
| GET `/api/replenishment/export` | Полный свежий план в CSV UTF-8 |

Запись принимает `application/json`. Материал: `code`, `name`, `category`, `unit`, `minimumStock`, `targetStock`. Поставщик: `name`, необязательный `contact`. Поступление: `number`, `materialId`, `supplierId`, `quantity`, `receivedOn` (YYYY-MM-DD), необязательный `note`. Числа передаются числами JSON. Пороги: `0 ≤ minimumStock ≤ targetStock ≤ 1 000 000`; количество: целое `1…1 000 000`; дата: 2000–2100, реально существующая.

Миграции находятся в `drizzle/`. `npm run db:generate` нужен при изменении схемы, `npm run db:migrate` применяет миграции. Применённые SQL не редактируются. В этом обновлении схема и миграции не менялись.
