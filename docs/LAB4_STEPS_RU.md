# ЛР №4 — актуальная проверка CI перед PR №1

Обновлено 16.11.2026. Verify / Publish уже присутствуют в dev. Создавать dev/prod и повторно публиковать подготовительные ветки не требуется. Факт выполнения ЛР №4 подтверждается реальными логами TeamCity и Docker Hub, а не наличием DSL.

## Источники и настройки

- Репозиторий: `https://github.com/VladislavG32/stockflow.git`.
- Source в `.teamcity/settings.kts`: `refs/heads/dev`, branchSpec `+:refs/heads/(*)`.
- Versioned Settings: отдельно сверить URL, root ID, default branch и каталог `.teamcity`. Для сопровождения после PR №1 использовать согласованную dev; `prep/lab4-ci` — сохранённая контрольная точка. Не менять сервер автоматически.
- Использовать текущие доверенные настройки проекта (Always use current settings); проверить, что произвольная ветка сборки не подменяет DSL. Фактическое значение на сервере неизвестно.
- Verify и Publish должны работать на `stockflow-build-agent` отдельного Linux CI. Тяжёлую сборку не переносить на TEST/STAGE/PROD.

## Что проверить в UI TeamCity без запуска

1. `StockFlow_Verify`: checkout On agent / clean, шаг `bash scripts/ci/verify.sh`, VCS trigger на все ветки, артефакты `checks/ci-images.*`.
2. `StockFlow_Publish`: только dev / `<default>` / prod, успешный Verify, snapshot dependency и артефакты той же цепочки. Шаг `bash scripts/ci/publish.sh` не пересобирает образы.
3. Только у Publish: Password `env.DOCKERHUB_USER`, Password `env.DOCKERHUB_TOKEN` с правом записи в нужный repository; `env.IMAGE_REPO=<login>/stockflow` вместо `SET_DOCKERHUB_USER/stockflow`. Проверять наличие и область действия, не раскрывать значения. У Verify и родителей проекта Hub-секретов быть не должно. `credentialsJSON` привязаны к конкретному серверу, не переносить ссылки с другого TeamCity.
4. Проверить наследуемые настройки, шаблоны, дополнительные триггеры, очередь и фактические последние SHA. Текущий DSL содержит только Verify / Publish, без Stage/Prod deploy.

Merge PR №1 в dev по текущему DSL запускает Verify, затем успешный Verify может запустить Publish с тегами `dev-<полный SHA>` и `dev-<полный SHA>-migrator`. Если публикация сейчас запрещена, до merge администратор должен приостановить автоматический Publish и проверить очередь. Эти действия в данной подготовке не выполнялись.
