# StockFlow: руководство для защиты

## 1. Что и на каком этапе сделано

StockFlow — учебная система автоматизации складского учёта Московского Политеха для дисциплины «Автоматизация процессов жизненного цикла программных средств».

ЛР №2 представлена исходным коммитом `1fbdd2b67a434f1fb727c7c79e87f56c3ba1254f`. Тогда существовали статическая главная страница, четыре демонстрационных раздела и `/api/health`. В этой версии не было базы и контейнеров. Новые возможности относятся к ветке `feature/lab3-stockflow` и этапу подготовки к ЛР №3. Старые отчёты не изменяются.

На текущем этапе реализованы создание и просмотр материалов, поставщиков и поступлений, изменение порогов запаса, вычисление остатков, поиск, фильтры и план пополнения. Авторизации, списаний, резервирования, удаления операций, заказов поставщикам, TeamCity, Docker Hub и CI/CD пока нет. Это сознательные границы учебного проекта, а не возможности, якобы существовавшие в ЛР №2.

## 3. Как работает Next.js-приложение

Next.js использует App Router: расположение `src/app/api/materials/route.ts` задаёт адрес `/api/materials`, а экспортированная функция `POST` обслуживает POST-запрос.

`page.tsx` — серверный компонент. Он выполняется на сервере и обращается к базе через `getDashboard()`. В браузер передаются уже готовые данные, а не пароль подключения и не соединение с PostgreSQL. `dynamic = "force-dynamic"` означает, что снимок читается при открытии страницы. Сборка не пытается получить данные из базы.

`Dashboard` и формы используют `"use client"`: им нужны состояние React, обработчики событий и браузерный `fetch`. Это не переносит код PostgreSQL в браузер: клиент импортирует только JSON-типы и компоненты, а обращения к БД остаются в серверных маршрутах.

В `layout.tsx` указан `lang="ru"`. В оболочке есть навигация по якорям, ссылка пропуска меню для клавиатуры и сообщение об учебном назначении. Все четыре прежних раздела сохранены, а пятый раздел — новая функция ЛР №3.

## 4. Путь данных от формы до PostgreSQL

Пример: регистрация пяти упаковок бумаги.

1. Пользователь выбирает материал и поставщика, вводит уникальный номер, количество `5` и дату.
2. `RecordForm` перехватывает отправку и собирает `FormData`.
3. Числовые поля преобразуются в числа JSON. Пустое число становится `null`, а не незаметно нулём.
4. Браузер отправляет `POST /api/receipts` с `Content-Type: application/json`.
5. `readJson()` ограничивает тело 16 КиБ, проверяет тип содержимого и браузерный Origin.
6. `createReceipt()` проверяет данные по `receiptSchema`.
7. Drizzle формирует параметризованный SQL INSERT. Значения не склеиваются в SQL-строку.
8. PostgreSQL проверяет ограничения: наличие материала и поставщика, уникальность номера, положительное количество.
9. После INSERT сервер возвращает HTTP 201 и ID записи.
10. Форма запрашивает `/api/dashboard`. Сервер заново считает остатки и рекомендации, а React обновляет связанные разделы.

Реальный фрагмент из `repository.ts`:

```ts
const values = receiptSchema.parse(input);
const [row] = await getDb().insert(receipts).values(values)
  .returning({ id: receipts.id });
return row;
```

`input` имеет тип `unknown`, потому что внешним данным нельзя доверять. `parse()` либо возвращает проверенные данные, либо выбрасывает `ZodError`. `returning()` возвращает ID только что сохранённой операции.

Одна вставка атомарна: либо запись целиком добавлена, либо нет. В этой версии операция содержит один материал. Многострочный документ потребовал бы отдельной таблицы документа и транзакции для всех его строк.

## 5. Модель базы данных

- `materials`: код, название, категория, единица измерения, минимальный и целевой запас.
- `suppliers`: уникальное название и контактная строка.
- `receipts`: номер, внешний ключ материала, внешний ключ поставщика, количество, календарная дата, примечание.

Связи: у одного материала может быть много поступлений; у одного поставщика может быть много поступлений. Поступление всегда относится к одному материалу и одному поставщику. PostgreSQL не даст создать запись с несуществующим внешним ключом.

В `materials` нет изменяемой колонки `balance`. Иначе при параллельных операциях пришлось бы синхронизировать журнал и остаток. Здесь журнал — источник истины.

Количество целое, от 1 до 1 000 000 на поступление. Для дробных килограммов или литров в будущем следует ввести PostgreSQL `numeric` и согласованную десятичную арифметику; округлять складские величины обычным float нельзя. В текущем интерфейсе правило целых единиц явно указано.

Дата поступления хранится как ISO-строка фиксированного формата `YYYY-MM-DD`, проверенная сервером, без часового пояса: это календарный день документа. Такая строка сортируется в хронологическом порядке. `created_at` — другой смысл: реальный момент сохранения, для него применяется `timestamp with time zone`.

## 6. Остатки и согласованность данных

Пока есть только поступления, формула остатка:

```text
остаток материала = SUM(количество всех его поступлений)
```

SQL-выражение в Drizzle:

```ts
balance: sql<string>`coalesce(sum(${receipts.quantity}), 0)`
```

`SUM` считает PostgreSQL, а `COALESCE` заменяет отсутствие операций нулём. `LEFT JOIN` оставляет в результате даже материал без поступлений. `GROUP BY materials.id` объединяет его операции. PostgreSQL возвращает сумму integer как bigint, драйвер — как строку; сервер преобразует её в число для JSON учебного интерфейса.

В `getDashboard()` чтение выполняется в транзакции `REPEATABLE READ`, `READ ONLY`: каталог, журнал и справочник отражают один снимок. Даже если параллельно пришло поступление, одна загрузка не покажет новый журнал вместе со старым остатком. Повторная загрузка увидит следующую актуальную версию.

Независимые вставки поступлений не теряются: никто не читает старый остаток, чтобы записать `старый + количество`. После сохранения итог считается суммой всех операций. Интеграционная проверка отправляет четыре поступления одновременно и проверяет итог.

Вкладки не получают события в реальном времени. После собственной записи данные обновляются автоматически; изменения из другой вкладки появляются при «Обновить данные» или перезагрузке страницы. При ошибке интерфейс предупреждает, что старый снимок может быть устаревшим.

## 7. Умный план пополнения

Это детерминированный алгоритм, а не искусственный интеллект. Он сравнивает остаток с порогом, установленным пользователем.

Реальная функция из `inventory.ts`:

```ts
export function replenishment(balance: number, minimumStock: number, targetStock: number) {
  const shortage = balance < minimumStock;
  return { shortage, recommended: shortage ? Math.max(0, targetStock - balance) : 0 };
}
```

Пример: минимум 10, цель 30, остаток 8. `8 < 10`, поэтому предупреждение активно и рекомендуется `30 − 8 = 22`. После поступления 22 остаток становится 30, рекомендация исчезает. При остатке ровно 10 дефицита нет: условие строгое. Если минимум равен нулю, отсутствие запаса не вызывает закупку. Цель не может быть ниже минимума.

Порог можно задать при создании материала или изменить в каталоге через «Пороги». После изменения повторно загружается снимок. Логика расчёта общая для интерфейса и CSV, поэтому экспорт не использует другую формулу.

План показывает только материалы с `shortage = true`, с учётом фильтров интерфейса. CSV всегда экспортирует полный свежий план из БД. В CSV есть UTF-8 BOM, разделитель `;`, экранирование кавычек и защита строк, начинающихся с формулы Excel. Экспорт не создаёт покупку, заказ или поступление автоматически.

## 8. Валидация и ошибки

Три уровня защиты:

1. HTML: обязательность полей, тип числа/даты, длина, min/max. Это удобство пользователя.
2. Zod на сервере: типы JSON, trimmed строки, длины, целочисленность, диапазон, дата и соотношение порогов. Эту проверку нельзя обойти изменением HTML.
3. PostgreSQL: UNIQUE, NOT NULL, CHECK, FOREIGN KEY. Это целостность уже хранимых данных.

`apiError()` преобразует ошибку PostgreSQL `23505` в HTTP 409 (дубликат), `23503` — в HTTP 400 (неверная связь), `23514` — в HTTP 400 (нарушено CHECK). Недоступность базы возвращает 503. Невалидный JSON получает 400, неверный Content-Type — 415, большой запрос — 413, неизвестный ID при изменении порогов — 404.

Drizzle может вложить исходную ошибку драйвера в `cause`, поэтому обработчик извлекает код оттуда. В ответе нет полного текста SQL, трассировки и строки подключения. При ошибке формы введённые значения сохраняются; при успехе форма создания очищается. На время запроса кнопка отключается. Уникальный номер операции предотвращает двойное поступление с тем же номером.

Если сеть оборвалась после отправки, нельзя достоверно знать, сохранился ли запрос. Следует обновить журнал и проверить номер, прежде чем отправлять запись повторно. Проверка Origin ограничивает нежелательные браузерные запросы, но НЕ заменяет авторизацию.

## 9. Контейнеризация

Docker запускает приложение в изолированном окружении с заданными зависимостями. Образ — шаблон файловой системы и настроек; контейнер — запущенный экземпляр образа. Виртуальная машина виртуализирует отдельную ОС, а Linux-контейнеры используют ядро Linux-хоста. В ЛР №3 Docker работает внутри уже подготовленных Ubuntu VM.

`Dockerfile` описывает несколько стадий:

- `dependencies`: `npm ci` по lock-файлу;
- `builder`: production-сборка Next.js;
- `migrator`: зависимости и SQL-файлы для одноразового применения миграций;
- `runner`: standalone-результат Next.js и статика, процесс без root.

Секреты не передаются в build и не копируются благодаря `.dockerignore`. Строка подключения поступает при запуске. Статическая сборка не требует доступной БД. `next.config.ts` включает `output: "standalone"`.

Compose описывает взаимодействие:

```text
PostgreSQL (healthy) → migrate (завершился с кодом 0) → app
```

`db` — имя сервиса и DNS-адрес внутри сети Compose. `localhost` внутри app означал бы сам app, а не PostgreSQL. Для локального Next.js вне контейнера используется `127.0.0.1` и дополнительный `compose.dev.yaml`.

`postgres_data` — именованный volume, смонтированный в каталог данных PostgreSQL 17. Он сохраняется после `docker compose down` и после пересоздания контейнеров. `down -v` удаляет volume и данные, поэтому для проверки сохранности его применять нельзя. Volume — не резервная копия: поломка диска VM всё ещё уничтожит данные.

`pg_isready` сообщает, что PostgreSQL принимает соединения. `/api/health` сохраняет старый контракт `{"status":"ok","service":"stockflow"}`. `/api/ready` дополнительно читает три таблицы и возвращает 503, если база или схема недоступна. Healthcheck контейнера app проверяет `/api/ready`.

Образы базы и Node закреплены по основным версиям; точные npm-зависимости закреплены lock-файлом. Для строго побитового повторения окружения в дальнейшем можно закрепить Docker-образы по digest. Команды развёртывания и доказательства сохранности описаны в `LAB3_STEPS_RU.md`.

## 11. Вопросы преподавателя

**Почему PostgreSQL, а не массив в React?** Массив исчезает при перезапуске и не является общим для пользователей. PostgreSQL хранит записи постоянно и поддерживает целостность, транзакции и параллельный доступ.

**Зачем Drizzle?** Он связывает TypeScript-описание таблиц, типизированные запросы и SQL-миграции. Это не отменяет знания SQL: JOIN, SUM, ограничения и транзакции всё ещё нужно понимать.

**Почему не сохраняете остаток отдельно?** Тогда пришлось бы синхронно изменять две сущности. При текущем масштабе сумма журнала проще и надёжнее. При большом объёме возможна отдельная модель агрегатов, но потребуется согласованное обновление.

**Что произойдёт с двумя одновременными поступлениями?** Каждая вставка сохранит свою строку. SUM учтёт обе. Уникальный номер защищает от повторения той же операции.

**Почему умный план — индивидуальная функция?** Пороги задаются для каждого материала; список закупок автоматически меняется на основе фактических операций, без ручного пересчёта. Алгоритм объясним и работает локально.

**Почему при остатке 10 и минимуме 10 нет закупки?** Требование говорит о недостатке относительно минимума. Недостаток реализован как строгое `<`, это закреплено тестом.

**Зачем миграции, если таблицы можно создать вручную?** Миграции — версия схемы вместе с кодом. На TEST, STAGE и PROD применяется один и тот же SQL в одинаковом порядке. Drizzle хранит журнал применённых миграций и не выполняет их повторно.

**Как схема меняется позже?** Изменить `schema.ts`, выполнить `npm run db:generate`, проверить SQL, создать новый коммит. Уже применённые миграции не редактировать. Для следующего запуска — `npm run db:migrate` или Compose.

**Зачем volume и почему не просто контейнер?** Слой контейнера заменяется при пересоздании. Volume имеет отдельный жизненный цикл и хранит кластер PostgreSQL.

**Почему TEST, STAGE и PROD не обмениваются данными?** Это разные VM с отдельными томами и отдельными конфигурациями. Одна версия кода проверяется последовательно, но базы не становятся общей базой автоматически.

**Защищён ли сервис для Интернета?** Нет. Это учебная система без пользователей и ролей. По умолчанию порт app доступен только на loopback, а на VM его следует привязать к host-only IP. Публикация в Интернет потребует авторизации, TLS и других изменений.

**Что проверено автоматически?** Lint, TypeScript, production build, формулы и валидация, настоящий API и PostgreSQL. Проверку контейнеров и VM следует отличать от локальных проверок — смотреть `VERIFICATION_RU.md`.
