## Навигация и формы

Причина дефекта: `aria-current` и заголовок верхней панели читались из `location.hash`. При Ctrl+Home / обычной прокрутке URL сохранялся, и выделение отставало от видимого содержимого.

Теперь текущий раздел рассчитывается по координатам разделов и `scroll-padding-top`. Обновление выполняется через requestAnimationFrame на scroll, resize, hashchange, pageshow и изменении размеров основного содержимого. В конце страницы учитывается последний раздел. URL не переписывается при ручной прокрутке; переходы назад и якоря остаются нативными.

Проверено в Chrome:

- Все шесть ссылок навигации: обзор, материалы, поставщики, поступления, остатки, план. Заголовок и активная ссылка соответствуют видимому разделу после завершения прокрутки.
- Возврат Ctrl+Home из остатков: hash остаётся `#balances`, но активен обзор, scrollY=0.
- PageDown без изменения hash: обзор сменяется материалами по фактической позиции.
- Обновление страницы сохраняет соответствие реальному восстановленному viewport; сам старый hash не назначает активный раздел.
- Прямое открытие URL с якорем и достижение конца страницы проверены на production-сборке.
- «+ Новая запись» остаётся в закреплённой верхней панели. Переход фокусирует `entry-title`; следующий Tab — создание материала. Проверены desktop и телефон.
- При недоступном снимке данных действие создания записи не ссылается на отсутствующую форму: показано disabled-состояние.

Использован `git merge-tree --write-tree`, затем git archive полученного дерева в отдельный временный каталог **без рабочего Git checkout и без перемещения веток**. Это проверка совместимости, а не merge в dev или выполнение доставки ЛР №5.

Разрешение конфликта во временной копии:

1. Сохранён новый dashboard из PR, включая навигацию, сортировку и формы.
2. `matchesStockFilter` из подготовки ЛР №5 используется внутри `materialView`, где теперь выполняется фильтрация. Импорт старого helper в dashboard не нужен.

Сохранён [патч разрешения](lab5-ui-compatibility.patch) для **будущей ветки ЛР №5**. Он меняет только dashboard и material-view; применять его в текущем PR без предварительного переноса `matchesStockFilter` из ЛР №5 не нужно.

Схема совпадает; в drizzle только `0000`, конфигураций TeamCity ровно три: Verify / Publish / Stage. Нет Acceptance, Gitleaks gate, цен, документов или миграций ЛР №6–8.

## Dev как ветка по умолчанию

Прочитаны настройки GitHub через API: default — `main`; `dev` существует на `b742e5a`, protected=false, repository rulesets — пустой список. Настройки **не менялись**.

Безопасный порядок после отдельного решения владельца:

1. Сначала согласовать и слить PR №1 в dev; убедиться в итоговом дереве, README, статусах проверок и отсутствии миграций будущих этапов.
2. Сохранить `main` на историческом `1fbdd2b`: **не переименовывать, не удалять и не force-push**. Смена default выбирает существующую dev, а не заменяет main её содержимым.
3. Настроить для dev разумную защиту от force-push/удаления и работу через PR. Обязательные status checks добавлять только для реально подключённых и завершающихся проверок; не требовать вымышленного независимого согласования в индивидуальном проекте.
4. Администратор: GitHub → Settings → Default branch → выбрать dev → Update → подтвердить предупреждение. Это отдельное последующее действие, а не часть текущего аудита.
5. Проверить, что главная страница показывает новый README, новые PR по умолчанию направляются в dev, а историческая main по-прежнему открывается по явной ссылке. PR №1 уже имеет явную базу dev.
6. На клиентах после смены выполнить `git fetch origin` и `git remote set-head origin -a` для обновления локального origin/HEAD. Это не двигает локальные ветки dev/prod, которые пока отстают от origin.

TeamCity Source в текущем DSL уже явно использует `refs/heads/dev`, поэтому одно изменение default на GitHub не требует переименования его Source. Автодоставки текущий PR не добавляет; перед любым merge в dev учитывать существующий Publish-триггер, если внешний TeamCity подключён.

Официальные инструкции: [GitHub — смена default branch](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/changing-the-default-branch), [защита веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
